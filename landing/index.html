I. Nature of the Action

When a judge has a conflict of interest, they recuse themselves from the case. This protocol gives that capacity to your smart contracts.

Existing token-safety services are centralized APIs. Every dApp that integrates them trusts a single vendor with the call to block or permit a transaction. Recuse Protocol replaces that trust assumption: live public evidence is written into a GenLayer Intelligent Contract, a deterministic rubric assigns a verdict, and the result becomes reusable on-chain state. The integrating contract consults the verdict and, when the evidence demands it, steps aside.

Recusal, in law, is not a refusal to act. It is the act of stepping aside so the proceeding may continue under proper authority. Likewise here: the protocol does not block trades. It produces an on-chain finding. The integrating contract decides what to do with it.
II. Parties

The actors before the court

Petitioner
The Integrating Contract
A DEX router, lending market, vault, or wallet that must decide, in the moment, whether to let a transaction proceed.
Respondent
The Token Under Review
An ERC-20 contract, named by address and chain, whose integrity is at issue. Newly deployed, established, or anywhere between.
Adjudicator
RecuseOracle on Bradbury
The deployed Intelligent Contract that receives evidence, applies the rubric, and stores the verdict for later reads.
Evidence
Live Public Sources
DexScreener and Honeypot.is data fetched at request time, plus token profile links for website, X, and GitHub signals.
III. Possible Dispositions

The four findings of this court

Each verdict is named for what the integrating contract should do upon receipt. The headline gate, should_recuse(), returns true only for the strictest finding - leaving softer verdicts to the policy of each consumer.

CLEAR
Proceed without restriction. Evidence is consistent with a legitimate, established token.
0 - 29
WATCH
Proceed but log. Soft warning to the user. Reassess sooner than the default cache interval.
30 - 59
FLAG
Hold. Require explicit user override. Surface the full reasoning before allowing the transaction.
60 - 79
RECUSE
Step aside. The transaction shall not proceed under the integrating contract's authority.
80 - 100
IV. Method of Fact-Finding

How a verdict is reached

I.
Live snapshot
The app fetches current DexScreener and Honeypot.is data through a serverless endpoint with no private key.
II.
Wallet transaction
The connected wallet submits assess_snapshot to RecuseOracle on Bradbury. No backend account writes verdicts.
III.
Stored verdict
The contract applies the rubric, persists CLEAR, WATCH, FLAG, or RECUSE, and exposes the result through get_verdict and should_recuse.

VI. Filings for Review

How to invoke the court

Two integration modes are supported. Pull is synchronous - the integrating contract consults the verdict before allowing a transaction. Push is asynchronous - subscribers receive updated verdicts when a keeper re-runs the assessment.

From another Intelligent Contract (Python)
# { "Depends": "py-genlayer:1jb45aa8ynh2a9c9xn3b7qqh8sm5q93hwfp7jqmwsfhh8jpz09h6" }
from genlayer import *

RECUSE = Address("0x...")  # deployed RecuseOracle

class SafeSwap(gl.Contract):
    @gl.public.write
    def swap_in(self, token: str, chain: str, amount: u256):
        oracle = gl.get_contract_at(RECUSE)
        if oracle.should_recuse(token, chain):
            raise gl.vm.UserError("Recuse: token failed integrity test")
        # ... proceed with swap
From a Solidity contract via LayerZero bridge
interface IRecuse {
    function shouldRecuse(address token, string calldata chain)
        external view returns (bool);
}

contract GuardedRouter {
    IRecuse constant RECUSE = IRecuse(0x...);

    function swap(address tokenOut, uint256 amt) external {
        require(!RECUSE.shouldRecuse(tokenOut, "base"), "blocked");
        // ... swap logic
    }
}
